# Builder engine audit: placement, movement, and acceptance tests

This is an evidence-based audit and test plan, not a claim that every building behavior is fixed.

## Hands: placement and interaction

### Changes in the staged source
1. Targeted placement prediction restores the player's original yaw/pitch in `finally`; a runtime exception from a modded `BlockItem` is debug-logged and skipped.
2. The inventory-wide `approxPlaceable` scan retains a block's default state if local placement prediction returns null or throws. The inventory throwaway selector also catches modded `BlockItem` prediction errors and falls back to block identity. Inventory matching is by block type; exact target-context placement is verified separately. If all temporary slots 1–7 are needed, the inventory behavior now uses a reversible swap to cycle stacks rather than no-op; unit tests cover candidate-slot selection. Placement prediction also accepts same-block manual-state differences (such as repeater delay, note, lever power, or wooden-door open state) so the block can be placed structurally and adjusted during the final interaction pass; block identity and structural/orientation differences remain strict.
3. Support-face sampling uses all six correctly oriented AABB faces, and a placement click requires the real raycast to match the exact support block and face. Mining also requires the real raycast to hit the intended block; approximate rotation alone cannot force a break. Failed clicks use increasing retry delays; waiting targets do not monopolize path goals, the builder keeps goals for retry-waiting targets and continues pathing toward them while cooldowns expire, and after five attempts with no target-state change it defers that target while continuing other work.
4. Repeated path calculation failures are bounded; a changed goal can be tried once, but the same goal failing twice without player/block progress pauses with diagnostic guidance.
5. Block-state property comparisons use `Objects.equals` instead of reference identity; runtime-derived repeater/comparator/wire power and neighbor-derived connection/shape properties are ignored during progress checks, while stable lever POWERED remains significant for the final interaction pass. Regression tests cover these distinctions, repeater locking versus delay, tripwire attachment, sculk-sensor phase, fence-gate `in_wall`, and downward connection states.
6. Litematica decoding accepts known Litematica format versions 1–7 using their shared core palette/packed-block-state schema, validates `SubVersion` for v6+, and rejects unknown future versions; it also uses checked 64-bit volume arithmetic and exact integer palette bit-width calculation; it rejects empty schematics, more than 4,096 regions, empty palettes, palettes above 65,536 entries, wrong palette-entry or `Properties` tag types, invalid/unknown block identifiers, unknown state-property names, invalid state-property values, invalid palette indices, truncated packed `BlockStates`, over-budget regions or aggregate schematics, excessive intermediate/column array allocations and composite bounding-box scan volume, and overflowing coordinates/extents. It allows unused/stale palette entries within the safe cap, validates only indices referenced by packed `BlockStates`, and counts `TileEntities`/`BlockEntities` and `Entities` records to warn that the builder does not restore these payloads.

7. The builder runs a structural pass before a final manual-interaction pass, so the scan's incorrect-position cap cannot cause it to toggle levers or doors before unseen structural work is complete. Deferred toggle coordinates are held in a separate set: they are marked visited during structural scans so unloaded chunks do not cause repeat travel, then their completion hashes are removed and they are re-queued at the final interaction boundary. Layered builds postpone that pass until structural layers are complete, clamp both the structural layer scan and the final interaction pass to `stopAtHeight`, then scan only the completed vertical range. Layer advancement and failed-layer skipping share the same clamped depth helper; the skip option cannot skip during the final manual-interaction pass or beyond the configured stop boundary. A manual toggle scan is also gated on the explicit final-interaction phase, not just the current capped incorrect-position list.
8. Stable right-click-adjustable mismatches for hand-operable doors, trapdoors, fence gates, levers, repeaters, comparators, note-block pitch, and daylight-sensor inversion are routed through verified right-clicks rather than breaking the existing block. Iron doors and iron trapdoors are treated as redstone-only openables, not clickable toggles. Open/closed remains a required state even when `buildIgnoreDirection` is enabled; that option cannot hide an iron trapdoor's unresolved redstone state. Waiting retries yield to other build work; exhausted failures are diagnosed. Temporary button pulses and externally powered flags are treated as derived state. An open-state mismatch on a redstone-powered door/trapdoor/gate remains outstanding but is deferred from clicking and breaking, with a power-source diagnostic if no other work remains.

These changes improve defensive behavior; they do not guarantee that every modded block can be predicted or placed.

### Cases that still require acceptance tests
- Face/raycast accuracy on partial collision shapes (slabs, stairs, fences, trapdoors, walls), including whether the failed-approach exclusion improves recovery without hiding genuinely reachable placements.
- Direction-dependent placement (stairs, logs, repeaters, observers, pistons, dispensers).
- Support dependencies and placement order (torches, rails, buttons, redstone components, plants); the builder now defers goals until `canSurvive` succeeds, but this still needs acceptance testing.
- Neighbor-derived states (dust, fences, walls, panes) after surrounding blocks update; confirm the derived-state comparison does not hide missing connections in the acceptance circuit.
- Inventory refill and slot selection when required items are in the main inventory rather than the hotbar; selected slots are checked against the requested stack after a swap, movement remains in `ATTEMPTING` until the stack is selected, and inventory clicks are deferred while a non-inventory container is open; queued swaps keep priority over automatic tool/throwaway moves, only one automatic move is initiated per tick, and stale swaps are dropped if the source stack vanished or slot indices are invalid.
- Server rejection and delayed block updates still need in-game acceptance testing to tune retry behavior and false positives.
- Stateful interaction timing needs live testing, especially paired door halves and levers affected by external redstone.
- Fluids, environmental requirements, and block-entity contents; these need separate support work.

## Feet: movement and reachability

The inspected BuilderProcess searches for nearby placements before assembling schematic goals. It now uses a placement-approach goal that excludes positions where a compatible hotbar item previously failed to find a valid placement face; these exclusions reset when the target or adjacent support states change. Nearby targets are skipped only when their unit AABB intersects the player's actual bounding box. Repeated path-calculation failures are also bounded when the same goal makes no progress. PathExecutor recalculates movement break/place/walk-into sets after world changes, checks changed movement costs, and cancels paths when movements become impossible or time out. Off-path distance and movement-recalculation timing diagnostics now use Baritone debug logging instead of printing to standard output.

No broad pathfinding algorithm or movement-cost rewrite is included. Before changing those heuristics, record a reproducible stuck case: start position, target block, surrounding blocks, selected movement, and relevant log output. Movement-cost changes can affect general path quality and safety.

## Acceptance test sequence

1. Static structure: foundation, walls, stairs, doors, and torches.
2. Direction-sensitive blocks: logs, stairs, repeaters, observers, pistons.
3. Redstone updates: adjacent dust, a repeater line, and lever/lamp output; verify after neighbor updates.
4. Inventory: required blocks partly in main inventory, not hotbar.
5. Unreachable support: builder gives a clear failure/pause rather than retrying an impossible placement indefinitely.
6. Pathing: reach a placement vantage point around obstacles without mining required support blocks or unsafe movement.
7. Malformed Litematica data: reject zero or more than 4,096 regions, zero dimensions, over-budget regions/aggregate schematics or composite bounding-box scan volume, overflowing signed coordinates/extents, missing palettes, wrong palette-entry/`Properties` tag types, unknown block identifiers or properties, invalid property values or palette indices, and truncated packed data cleanly, including tiny regions separated by enormous coordinate gaps.
8. Loader integration: decode minimal one-block, two-block, and separated multi-region Litematica NBT structures; reject an invalid packed palette index through the actual constructor/decode path; test cross-word packed data and unsupported-payload warnings for block entities/entities, including malformed payload tag types.
9. Calculator milestone: first build and verify a tiny combinational circuit, then a one-bit adder, then a small multi-bit adder with test inputs/outputs. Do not jump directly to a 64-bit calculator.

## Verification boundaries

The GitHub Actions workflow validates the integrated source snapshot by running the repository's Gradle unit tests and building the Fabric remapped JAR on Java 21. The unit tests exercise deterministic helper logic (schematic volume bounds, placement retry/backoff, support-face selection, state comparison, manual interaction classification, inventory-slot selection, and player/approach geometry). The workflow also packages the exact patched source and generated diff.

These checks do **not** launch a Minecraft client or server, simulate real player clicks against a live world, or prove that a complete redstone calculator works. Real-world acceptance testing is still required for server-side interaction acceptance, all block placement/support combinations, inventory changes, movement recovery, and a powered end-to-end circuit. No claim of full calculator correctness should be made until those in-game tests pass.
